# AI Memory 开源项目调研 Brief

## 1. 目标问题

评估能够在多个开发 Agent 之间沉淀项目业务知识、技术决策和经验证开发经验的开源 Memory 项目，并判断哪些设计可用于把开发会话转化为可追溯的 Skill 更新候选。重点关注记忆写入、组织、召回、来源追踪、模型接口切换和单机/内网自托管边界。

## 2. 必须能力

- 支持项目级长期 Memory，并能按 Agent、成员或项目范围检索。
- 支持从经授权的开发会话或外部事件中提取知识、经验或 Skill 候选。
- 支持可切换的 LLM/Embedding 接口，明确兼容端点、模型和向量维度限制。
- 支持单机或一台内网服务器部署，并说明运行组件、持久化和外部依赖。
- 对每个项目明确开源核心、商业/SaaS 边界、已满足能力和需要外部补齐的治理能力。

## 3. 硬约束

- 部署环境：优先本地或单台内网服务器，不以必须使用 SaaS 为前提。
- 安全、隐私和数据边界：原始会话是否上传由用户或外部治理层控制；必须区分原始证据、派生 Memory 和 Skill。
- 许可证边界：必须核对仓库许可证以及开源核心与商业能力的边界。
- 不接受的外部服务或依赖：不能把不可替代的托管服务、未公开的核心引擎或企业能力算作开源自托管能力。
- 其他不可妥协条件：事实、设计判断和适配结论必须能追溯到一手资料；未知能力标记为“未确认”。

## 4. 可接受缺口

- 可以通过配置或常规接入补齐的部分：LLM/Embedding Base URL、向量后端和 Agent 适配器。
- 可以接受的适配或自研范围：会话选择、来源元数据、权限、审批、Skill 候选 Git 流程和回归验证。
- 可以暂不具备的能力：项目本身不必内置完整原始会话上传、团队审批或 Skill 自动发布，但必须明确边界。

## 5. 解决思路与使用偏好

- 偏好的架构或产品形态：可组合的 Memory 层，优先可读、可重建、可追溯的知识载体。
- 偏好的部署方式：单机优先，可按规模增加 PostgreSQL/pgvector、图数据库或队列。
- 数据与隐私偏好：原始会话与派生知识分开存储，默认本地，上传前有明确授权。
- 偏好的集成方式：SDK、HTTP、MCP 或 Agent Hook，能够由外部适配器接入多个 Agent。
- 可接受的基础设施：SQLite、PostgreSQL/pgvector、单机向量库和必要的本地模型运行时。
- 不接受的外部依赖：未公开的托管后端不能作为自托管方案的必要组件。

## 6. 社区与项目成熟度偏好

- 许可证偏好：优先 MIT、Apache-2.0；其他许可证必须说明使用和分发边界。
- 维护活跃度要求：核对最近提交、Release 和动态信息，记录核验日期。
- 官方文档要求：关键能力至少有官方 README、文档、源码或部署清单支撑。
- 社区规模或采用情况偏好：Stars 和采用情况只用于排序和说明，不替代需求契合度。

## 7. 候选发现偏好

- 是否需要自动发现候选项目：否；本批次使用已确认的十个主清单项目。
- Stars：排序参考，不作为硬约束。
- 最近维护：排序参考；长期不维护时说明风险。
- 技术栈或语言：不限，但需能说明自托管运行时。
- 是否必须自托管：是，至少要有可核验的本地或单机路径。
- 是否必须存在官方文档：是，关键事实必须有一手来源。
- 候选项目数量上限：10
- 深度调研数量上限：10
