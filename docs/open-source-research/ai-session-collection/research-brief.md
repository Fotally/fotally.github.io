# AI 开发会话收集开源项目调研 Brief

## 1. 目标问题

评估能够发现、采集、标准化、回放和分析 Claude Code、Codex、Cursor 等开发 Agent 会话的开源项目，并判断哪些项目能为经验提取、项目 Memory 和 Skill 更新提供可追溯原始证据。重点关注本地会话发现、Hook/OTel 接入、会话与工具事件模型、隐私控制、单机部署和评估闭环。

## 2. 必须能力

- 能记录或接收开发 Agent 的会话、用户提示、模型响应、工具调用及必要的文件/测试上下文。
- 能按 session、project、agent 或 commit 查询、回放或导出记录。
- 尽量支持多个 Agent，或提供可扩展的 adapter、Hook、SDK、HTTP 或 OTel 接口。
- 支持单机或一台内网服务器部署，并列出运行组件、持久化和外部依赖。
- 对隐私、原始数据、脱敏、许可证和开源/商业边界给出可复核说明。
- 为后续 Memory 提取和 Skill 候选治理保留稳定的来源标识，但不要求项目自动发布 Skill。

## 3. 硬约束

- 部署环境：优先本地或单台内网服务器，不以必须使用外部 SaaS 为前提。
- 安全、隐私和数据边界：完整原始会话的上传应由用户或外部治理层明确授权；默认本地保存优先。
- 许可证边界：核对 SDK、服务端、Dashboard、企业目录和托管服务是否使用不同许可证。
- 不接受的外部服务或依赖：未公开的核心后端不能被描述为开源自托管能力。
- 其他不可妥协条件：区分官方声明、源码事实和调研判断；动态信息注明核验日期。

## 4. 可接受缺口

- 可以通过配置或常规接入补齐的部分：Agent 适配器、JSONL/SQLite 导入器、OTel Collector transform 和公司 API 端点。
- 可以接受的适配或自研范围：本地选择/预览、脱敏、原始对象存储、上传审批、权限审计、Memory/Skill 治理。
- 可以暂不具备的能力：项目本身不必同时提供业务 Memory、Skill PR 和回归评估，但必须明确其职责边界。

## 5. 解决思路与使用偏好

- 偏好的架构或产品形态：本地采集端与中央分析/治理层解耦，原始证据和标准化 Trace 分层保存。
- 偏好的部署方式：单机优先，可按会话量增加数据库、对象存储、队列或 OTel Collector。
- 数据与隐私偏好：支持采集模式、敏感字段过滤、用户选择和可撤回的上传控制。
- 偏好的集成方式：优先原生 Hook、MCP、SDK、HTTP 或 OpenTelemetry。
- 可接受的基础设施：SQLite、PostgreSQL、ClickHouse、对象存储和单机 Collector。
- 不接受的外部依赖：不能把团队 SaaS、未开放控制面或商业版专属功能写成 OSS 必需能力。

## 6. 社区与项目成熟度偏好

- 许可证偏好：优先 MIT、Apache-2.0；ELv2、AGPL 等必须单独说明。
- 维护活跃度要求：核对最近提交、Release 和动态信息，记录核验日期。
- 官方文档要求：关键采集、存储、检索和部署事实必须有一手来源。
- 社区规模或采用情况偏好：Stars 和采用情况只用于排序与说明，不替代需求契合度。

## 7. 候选发现偏好

- 是否需要自动发现候选项目：否；本批次使用已确认的十个主清单项目。
- Stars：排序参考，不作为硬约束。
- 最近维护：排序参考；长期不维护时说明风险。
- 技术栈或语言：不限，但需能说明采集端和服务端运行时。
- 是否必须自托管：是，至少要有可核验的本地或单机路径。
- 是否必须存在官方文档：是，关键事实必须有一手来源。
- 候选项目数量上限：10
- 深度调研数量上限：10
